# 接口自动化测试平台 0-1 开发文档

> 文档定位：本文保存项目从 0 到 1 阶段的设计目标和开发基线，不再作为当前版本唯一的运行与使用说明。项目已经在该基线之上增加数据工厂、独立 WebSocket 交互、SSE 实时日志、仪表盘统计和统一交互组件等能力；当前功能、安装和部署方式以项目根目录 `README.md` 及实际代码为准。项目已于 2026-09 迁移到 Python 3.12 并完成依赖安全升级，本文第 2 节中关于 Python 3.8.8rc1 的版本约束只代表当时的开发基线，不再适用。

你现在是一名资深全栈工程师，请帮我从零开始，使用 Python 开发一个**接口自动化测试平台**。

本文档是项目开发的唯一规格说明。后续生成代码时，请严格按照本文档分阶段开发，不要一次性输出或生成完整项目。每个阶段完成后，需要说明完成内容、涉及文件、运行方式、验证方式和下一阶段建议。

## 1. 项目目标

开发一个易理解、易部署、界面美观实用的接口自动化测试平台，支持 HTTP 接口测试、WebSocket 接口测试、项目/接口/用例/集合/任务管理、断言、参数提取、全局变量、定时执行、通知、历史报告和测试数据工厂。数据工厂的当前实现边界和使用方式见[数据工厂功能说明](./数据工厂功能说明.md)。

平台主要面向不熟悉复杂前端框架的使用者，因此采用 Flask 服务端渲染页面，不使用 Vue、React 等前端工程化框架。

## 2. 技术栈约束

- Python 版本：必须基于用户本地版本 **Python 3.8.8rc1** 开发和验证。
- 后端框架：Flask，使用应用工厂和 Blueprint 组织模块。
- 数据库：MySQL 5.7，ORM 使用 SQLAlchemy。
- 数据库迁移：Flask-Migrate / Alembic。
- 任务调度：APScheduler，集成在 Flask 应用中。
- HTTP 请求：requests。
- WebSocket 客户端：websocket-client。
- JSONPath：jsonpath-ng。
- 表单和页面：Jinja2 模板 + Bootstrap 5 + jQuery。
- 邮件通知：Flask-Mail 或 Python 标准 smtplib，优先使用 Flask-Mail。
- 钉钉通知：requests 调用机器人 webhook。
- Redis：可选，不作为第一版强依赖。第一版优先使用 MySQL 持久化数据。
- 部署：项目完成后必须支持 Docker 和 docker compose 部署。

### Python 3.8.8rc1 和依赖约束

- 本项目开发、运行、测试默认使用用户当前已经准备好的隔离环境，Python 版本为 3.8.8rc1。
- 当前隔离环境初始状态可能没有安装第三方模块，后续开发时需要按项目实际需要自行安装依赖。
- 编写 `requirements.txt` 时必须选择兼容 Python 3.8 的版本，不能使用仅支持 Python 3.9+、3.10+ 的依赖版本。
- 如果某个库的最新版不兼容 Python 3.8，需要主动锁定可用版本，并在 README 中说明原因。
- 代码不能使用 Python 3.9+ 才支持的语法，例如内置泛型写法 `list[str]`、字典合并运算符 `|`、`match/case` 等。
- 类型标注如需使用泛型，请从 `typing` 导入 `List`、`Dict`、`Optional`、`Any` 等。
- 后续开发阶段如果需要新增第三方依赖，由开发者自行在当前隔离环境中安装，并同步更新 `requirements.txt`。
- 阶段完成说明中需要列出本阶段新增或调整的依赖。
- 第一版建议依赖版本需要优先考虑稳定和 Python 3.8 兼容，例如 Flask 2.x、SQLAlchemy 1.4.x、Flask-SQLAlchemy 3.0.x 或兼容版本、Werkzeug 2.x。

### MySQL 5.7 特别约束

- 默认字符集使用 `utf8mb4`，排序规则建议 `utf8mb4_unicode_ci`。
- 存储引擎使用 InnoDB。
- MySQL 5.7 不依赖 CHECK 约束，枚举值校验放在 Python 层处理。
- JSON 字段可以使用 MySQL 5.7 的 JSON 类型；如果本地 MySQL 小版本不支持 JSON，则允许降级为 LONGTEXT，并在应用层做 JSON 序列化。
- 避免使用 MySQL 保留字作为字段名，例如 `key`、`order`。变量名字段使用 `var_key`，排序字段使用 `sort_order`。
- 所有时间字段使用 `DateTime`，建议存储本地时间或 UTC 时间时保持全项目一致。

## 3. 必须实现的功能

### 3.1 HTTP 接口测试

- 支持 GET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS 等常见 HTTP 方法。
- 每个接口可以配置请求方法、URL、请求头模板、请求体模板、接口类型。
- 测试用例可以覆盖接口默认请求头、请求参数和请求体。
- 请求体支持 JSON、form-urlencoded、raw text 三种常见形式。
- 执行时记录请求 URL、请求头、请求体、响应状态码、响应头、响应体、耗时和异常信息。

### 3.2 WebSocket 接口测试

- 接口类型支持 HTTP 和 WebSocket。
- WebSocket URL 同样支持全局变量和临时变量替换。
- WebSocket 执行引擎必须采用**全双工执行逻辑**，不能实现为简单阻塞式“发送一条、等待一条”的线性逻辑。
- 建立连接后，需要启动独立的接收循环，持续监听服务端消息；发送动作和接收动作互不阻塞。
- 接收循环需要把消息写入线程安全的消息队列或消息缓冲区，断言逻辑基于该消息缓冲区在指定时间窗口内匹配消息。
- WebSocket 用例执行时允许在等待消息的同时继续发送后续消息，适配服务端主动推送、异步响应、多消息乱序返回等场景。
- WebSocket 用例支持多步骤配置：
  - connect：建立连接。
  - send：发送文本或 JSON 消息。
  - receive_assert：从消息缓冲区中在指定超时时间内匹配消息并执行断言。
  - close：主动断开连接。
- WebSocket 断言完成后必须主动关闭连接，即使执行失败也需要在 finally 中关闭。
- WebSocket 调试时，需要返回连接状态、发送消息、收到的消息流、每一步耗时、断言结果和错误信息。

### 3.3 友好断言

断言必须对用户友好，前端不能要求用户写 Python 表达式。

支持的断言目标：

- HTTP 状态码。
- 响应头。
- 响应体 JSONPath 字段值。
- 响应体全文。
- 响应体类型：JSON / text / empty / binary 简化识别。
- 响应体长度。
- 响应耗时。
- WebSocket 收到的消息内容。

支持的比较器：

- 等于：equals。
- 不等于：not_equals。
- 大于：greater_than。
- 小于：less_than。
- 大于等于：greater_or_equal。
- 小于等于：less_or_equal。
- 包含：contains。
- 不包含：not_contains。
- 为空：is_none。
- 非空：is_not_none。
- 正则匹配：regex_match。
- 响应时间小于：time_less_than。
- WebSocket 在指定秒数内收到包含内容的消息：receive_contains_within。

断言结构建议：

```json
{
  "source": "body_json",
  "jsonpath": "$.data.id",
  "comparator": "equals",
  "expected": "1001",
  "value_type": "string",
  "timeout_seconds": null
}
```

断言失败时必须返回并展示：

- 断言名称或字段。
- 实际值。
- 期望值。
- 比较器。
- 失败原因。

调试完成后，如果响应体是 JSON，需要自动提取可选 JSONPath 列表，供前端点选使用。

### 3.4 参数提取和接口关联

- 测试用例支持后置提取器。
- 提取器从响应 JSON 中通过 JSONPath 提取值，保存为运行时临时变量。
- 后续接口的 URL、请求头、请求体、WebSocket 消息都可以通过 `${变量名}` 引用临时变量。
- 场景集合执行时，临时变量在集合上下文中共享。
- 单接口集合执行时，原则上每个用例互不依赖；如存在提取器，也只在当前执行上下文中使用。

提取器结构建议：

```json
{
  "jsonpath": "$.data.token",
  "variable_name": "token",
  "required": true
}
```

### 3.5 全局变量和环境

- 支持多个环境，例如 test、staging、prod。
- 全局变量可设置为全局级别，也可设置为项目级别。
- 常见变量包括 `base_url`、`token`、`cookie`、`ws_url`、`host`、`port`。
- URL、请求头、请求体和 WebSocket 消息支持 `{{变量名}}` 引用全局变量。
- 执行时先替换 `{{global_var}}`，再替换 `${runtime_var}`。
- 页面顶部提供当前环境选择，调试和执行时都需要带上环境参数。

### 3.6 接口调试

- 测试用例编辑页必须提供“调试发送”按钮。
- 点击后通过 jQuery Ajax 请求后端调试接口。
- HTTP 调试返回完整请求信息、响应头、响应体、状态码、耗时、断言结果、提取器结果。
- WebSocket 调试返回步骤时间线、发送消息、收到的消息流、断言结果、连接关闭状态。
- 断言失败时前端必须明确显示实际值和期望值。
- 调试结果区域需要使用 Bootstrap 样式，响应体和 WebSocket 消息流使用可滚动区域展示。

### 3.7 项目、接口和用例管理

- 支持项目管理：项目名称、描述、启用状态。
- 每个项目管理自己的接口库。
- 接口包含名称、类型、方法、URL、默认请求头、默认请求体、描述。
- 编写测试用例时先选择项目，再选择该项目下的接口。
- 用例包含名称、请求覆盖配置、断言、提取器、WebSocket 步骤。

### 3.8 测试集合

集合分为两类：

- 场景集合：用例按排序串行执行；中间某个用例失败则终止整个集合；需要记录中断步骤。
- 单接口集合：用例按排序执行；某个用例失败不影响后续用例；需要记录每个失败用例的原因。

集合创建时，需要从已有用例中多选并排序。

### 3.9 定时任务

- 支持任务名称、启用状态、执行环境、执行计划、关联测试集合、关联通知方式。
- 执行计划至少支持：
  - interval：每隔 N 秒或 N 分钟执行。
  - daily：每天固定时间执行。
  - cron：高级 cron 表达式。
- 任务由 APScheduler 管理，应用启动时从数据库加载启用任务。
- 任务新增、修改、禁用后，需要动态同步 APScheduler。
- 手动触发集合执行和定时任务执行都需要生成历史报告。

### 3.10 通知管理

通知方式作为独立菜单管理。

钉钉机器人配置：

- 名称。
- webhook。
- 加签 secret/token。
- Markdown 消息模板。
- 启用状态。

邮箱配置：

- 名称。
- SMTP 服务器。
- SMTP 端口。
- 是否使用 TLS/SSL。
- 发件人邮箱。
- 授权码或密码。
- 收件人列表。
- 消息模板。
- 启用状态。

创建任务时从通知配置中选择一个或多个通知方式。任务执行结束后自动发送通知，通知内容必须包含概要和 HTML 报告链接。

### 3.11 历史报告和 HTML 报告

- 每次执行任务或手动执行集合后，生成执行历史。
- 执行历史保存任务名称、执行环境、开始时间、结束时间、总数、成功数、失败数、错误数、状态。
- 执行详情保存集合、用例、接口、URL、方法、状态、耗时、失败原因、断言详情、响应摘要、WebSocket 消息摘要。
- 报告页面通过 Flask 路由访问，例如 `/reports/<history_id>`。
- 报告页面使用 Jinja2 渲染，展示概要、集合结果、失败详情、断言详情和执行耗时。
- 钉钉和邮件通知中必须附带报告链接。

### 模块边界要求

- `http_runner.py` 只负责 HTTP 请求执行、HTTP 响应解析和耗时记录。
- `websocket_runner.py` 只负责 WebSocket 连接、全双工收发、消息缓冲、超时匹配和主动关闭。
- `case_runner.py` 根据接口类型选择 HTTP 或 WebSocket runner，并统一执行断言和提取器。
- `suite_runner.py` 只负责编排多个用例，维护集合级临时变量上下文。
- `assert_engine.py` 不直接访问数据库，不直接发送请求。
- `variable_engine.py` 不直接发送请求，不执行断言。
- `scheduler_service.py` 不写具体测试逻辑，只调用 `suite_runner.py` 或任务执行入口。

## 5. 数据库表设计

以下设计为第一版推荐表结构。实现时可以适度补充字段，但不能减少核心能力。

### 5.1 project 项目表

- id：主键。
- name：项目名称，唯一或项目内唯一。
- description：描述。
- is_active：是否启用。
- created_at：创建时间。
- updated_at：更新时间。

### 5.2 environment 环境表

- id：主键。
- name：环境名称，例如 test、staging、prod。
- description：描述。
- is_default：是否默认环境。
- created_at。
- updated_at。

### 5.3 global_variable 全局变量表

- id：主键。
- project_id：项目 ID，可为空。为空表示所有项目可用。
- environment_id：环境 ID。
- var_key：变量名，避免使用 MySQL 保留字 key。
- var_value：变量值，Text。
- description：描述。
- is_secret：是否敏感变量。敏感变量前端列表默认脱敏展示。
- is_active：是否启用。
- created_at。
- updated_at。

建议唯一约束：`project_id + environment_id + var_key`。

### 5.4 interface 接口表

原文中的 `api` 可以使用，但推荐命名为 `interface`，避免和 Flask API 路由概念混淆。

- id：主键。
- project_id：项目 ID。
- name：接口名称。
- interface_type：http / websocket。
- method：HTTP 方法。WebSocket 可为空或 WS。
- url：接口 URL 或路径，支持 `{{变量}}`。
- headers_template：JSON，请求头模板。
- body_template：JSON，请求体模板。
- body_type：json / form / raw / none。
- description：描述。
- is_active：是否启用。
- created_at。
- updated_at。

### 5.5 test_case 测试用例表

- id：主键。
- project_id：项目 ID。
- interface_id：接口 ID。
- name：用例名称。
- request_params：JSON，用例级参数。
- headers_override：JSON，用例级请求头覆盖。
- body_override：JSON，用例级请求体覆盖。
- assertions：JSON 数组。
- extractors：JSON 数组。
- ws_steps：JSON 数组，仅 WebSocket 用例使用。
- timeout_seconds：请求超时时间。
- description：描述。
- is_active：是否启用。
- created_at。
- updated_at。

### 5.6 suite 测试集合表

- id：主键。
- project_id：项目 ID。
- name：集合名称。
- suite_type：scene / single。
- description：描述。
- is_active：是否启用。
- created_at。
- updated_at。

### 5.7 suite_case 集合用例关联表

- id：主键。
- suite_id：集合 ID。
- case_id：用例 ID。
- sort_order：执行顺序，避免使用 MySQL 保留字 order。
- created_at。
- updated_at。

建议唯一约束：`suite_id + case_id`。

### 5.8 scheduled_task 定时任务表

原文中的 `task` 可使用，但推荐命名为 `scheduled_task`，语义更清晰。

- id：主键。
- name：任务名称。
- environment_id：执行环境 ID。
- schedule_type：interval / daily / cron。
- interval_seconds：间隔秒数，interval 模式使用。
- daily_time：每天执行时间，daily 模式使用，格式 HH:MM。
- cron_expression：cron 表达式，cron 模式使用。
- enabled：是否启用。
- next_run_at：下次执行时间。
- last_run_at：上次执行时间。
- created_at。
- updated_at。

### 5.9 task_suite 任务集合关联表

- id：主键。
- task_id：任务 ID。
- suite_id：集合 ID。
- sort_order：执行顺序。
- created_at。
- updated_at。

### 5.10 notification 通知配置表

- id：主键。
- name：通知名称。
- notification_type：dingtalk / email。
- config：JSON，保存 webhook、secret、smtp、recipients 等配置。
- message_template：Text，可为空。
- is_active：是否启用。
- created_at。
- updated_at。

## 6. 核心服务设计

### 6.1 variable_engine.py

必须提供：

- `build_variable_context(project_id, environment_id, runtime_vars=None)`：加载全局变量和项目变量。
- `replace_variables(value, context)`：递归替换字符串、字典、列表中的变量。
- 替换顺序：先替换 `{{var}}`，再替换 `${var}`。
- 找不到变量时不要静默失败，需要返回未替换变量列表或抛出友好异常。

### 6.2 jsonpath_service.py

必须提供：

- `extract_by_jsonpath(data, jsonpath_expr)`：根据 JSONPath 获取值。
- `list_jsonpaths(data)`：调试后枚举 JSON 响应中可点选的路径。

### 6.3 assert_engine.py

必须提供：

- `assert_response(assertions, response_context)`：执行断言并返回列表。
- `response_context` 需要兼容 HTTP 和 WebSocket。
- 每条断言结果必须包含 passed、actual、expected、comparator、message。

### 6.4 http_runner.py

必须提供：

- `run_http_case(case, context)`：执行 HTTP 用例。
- 使用 requests。
- 记录完整请求响应。
- 支持超时。
- 不处理 WebSocket。

### 6.5 websocket_runner.py

必须提供：

- `run_websocket_case(case, context)`：执行 WebSocket 用例。
- 使用 websocket-client。可以使用 `WebSocketApp` 回调模型，或使用后台接收线程配合线程安全队列实现。
- 必须采用全双工执行模型：
  - 连接成功后立即启动独立接收循环。
  - 接收循环持续接收服务端消息，并记录消息内容、时间戳、消息类型和异常。
  - 发送步骤只负责发送消息，不直接阻塞等待指定响应。
  - 断言步骤从消息缓冲区中按超时时间查找符合条件的消息。
  - 用例执行过程中，接收循环和发送步骤可以同时进行。
- 禁止实现为简单阻塞式“send 后 recv 一次”的线性逻辑。
- 支持连接、发送、异步接收、消息缓冲区断言、关闭。
- 用 try/finally 保证主动关闭连接。
- 不处理 HTTP。

### 6.6 case_runner.py

必须提供：

- `run_case(case_id, environment_id, runtime_vars=None, debug=False)`。
- 根据接口类型分派到 HTTP 或 WebSocket runner。
- 执行变量替换。
- 执行断言。
- 执行提取器。
- 返回统一结构，供调试、集合执行、报告生成复用。

### 6.7 suite_runner.py

必须提供：

- `run_suite(suite_id, environment_id, history_id=None)`。
- 场景集合：失败即停止。
- 单接口集合：失败继续。
- 维护集合级 runtime_vars。
- 返回集合执行概要和详情。

### 6.8 scheduler_service.py

必须提供：

- 应用启动时加载 enabled 任务。
- 新增、修改、禁用任务时同步 APScheduler。
- 定时任务触发后调用统一执行入口。

### 6.9 report_service.py

必须提供：

- 创建 execution_history。
- 写入 execution_detail。
- 汇总统计。
- 渲染 HTML 报告。
- 生成报告访问链接。

### 6.10 notifier.py

必须提供：

- 钉钉 Markdown 通知。
- 邮件 HTML 通知。
- 通知内容包含执行概要、失败数量、报告链接。
- 通知异常不能影响测试执行结果，但需要记录日志。

## 9. Docker 部署要求

项目最终必须提供 Docker 部署方案。

### 9.1 Dockerfile 要求

- 使用 Python 3.8 系列镜像，例如 `python:3.8-slim`。Docker 官方镜像通常不提供 `3.8.8rc1` 这种 rc 小版本标签，因此 Docker 部署可使用 Python 3.8 稳定镜像，但代码和依赖必须保持与本地 Python 3.8.8rc1 兼容。
- 设置工作目录 `/app`。
- 安装 requirements。
- 暴露 Flask/Gunicorn 运行端口。
- 生产启动建议使用 gunicorn。

### 9.2 docker-compose.yml 要求

必须包含：

- web：Flask 应用服务。
- mysql：MySQL 5.7 服务。

MySQL 服务建议：

- 镜像：`mysql:5.7`。
- 设置 `MYSQL_ROOT_PASSWORD`、`MYSQL_DATABASE`、`MYSQL_USER`、`MYSQL_PASSWORD`。
- 挂载数据卷。
- 设置字符集参数：`--character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci`。

web 服务要求：

- 通过环境变量读取数据库连接。
- 依赖 mysql 服务。
- 暴露应用端口，例如 5000。

### 9.3 .env.example 要求

至少包含：

```text

DATABASE_URL=mysql+pymysql://api_user:api_password@mysql:3306/api_test_platform?charset=utf8mb4
MAIL_SERVER=

MAIL_USE_SSL=true
MAIL_USERNAME=

BASE_REPORT_URL=http://localhost:5000
```

## 10. 代码规范

- Python 变量名、函数名、类名使用英文。
- Python 注释和 docstring 可以使用中文，复杂逻辑必须有简短中文说明。
- 遵循 PEP 8。
- 所有服务函数必须有 docstring。
- 数据库操作使用 SQLAlchemy ORM，不直接拼接原始 SQL。
- 所有 API 路由统一使用 `/api/` 前缀并返回 JSON。
- 页面路由返回模板。
- 前端 Ajax 错误需要显示用户可理解的错误信息。
- 用户输入展示到页面时必须转义，避免 XSS。
- 密码、token、SMTP 授权码等敏感信息通过环境变量或数据库加密/脱敏展示处理。
- 日志需要记录关键执行过程，但不能明文输出敏感变量。
