# 平台对接 CI 方案

> 文档定位：规划平台如何作为业务服务的质量门禁（CI）使用。本文只讨论方案与待决策问题，具体实现细节在进入开发前单独设计。
>
> 相关文档：[技术债与升级计划](./技术债与升级计划.md)

## 1. 定位

平台存在两种截然不同的“CI”，需要明确区分，避免混谈：

| | 平台自身的 CI | 平台作为业务服务的 CI |
|---|---|---|
| 保护对象 | 平台自己的代码 | 被测的业务服务（如用户服务） |
| 触发时机 | 平台代码提交 | 业务服务提交并完成部署 |
| 作用 | 防止改动引入回归 | 把接口测试变成发布流水线中的质量门禁 |
| 性质 | 工程卫生，成本极低 | 产品能力升级 |

本文聚焦右侧这一项。左侧仅在[技术债与升级计划](./技术债与升级计划.md)的 TD-3 中记录，作为低成本工程改进，不作为本方案的重点。

## 2. 目标链路

期望的完整链路：

```text
业务服务提交代码
    → 流水线构建并部署到测试环境
    → 部署完成后调用平台接口，触发该服务对应的用例集合
    → 平台执行集合，产出执行结果与报告
    → 平台把结论回传流水线（通过 / 失败 + 报告链接）
    → 流水线据此决定是否放行（质量门禁）
```

行业参照：Postman Monitor、Apifox、MeterSphere 均采用这一模式，都可被 Jenkins、GitLab CI 等流水线调用。自研平台的优势在于可以贴合自身业务的服务划分、环境规则与数据准备方式。

## 3. 现有能力盘点

以下能力当前已经具备，是实现本方案的基础：

| 能力 | 现状 | 代码位置 |
|---|---|---|
| 集合执行入口 | 已有 `POST /api/test-suite/execute` | `app/blueprints/suites.py` |
| 集合与步骤编排 | 支持场景集合、单接口集合、步骤级覆盖 | `app/models.py`（Suite / SuiteCase） |
| 环境管理 | 多环境、环境基础地址、环境类型 | `app/models.py`（Environment） |
| 变量体系 | 全局变量、项目变量、运行时提取变量 | `app/services/variable_engine.py` |
| 执行历史与明细 | 汇总统计、完整请求响应快照、断言明细、耗时 | `ExecutionHistory` / `ExecutionDetail` |
| 报告 | 生成 HTML 报告与报告链接 | `app/services/report_service.py` |
| 通知渠道 | 钉钉、邮件 | `app/services/notifier.py` |
| 定时调度 | APScheduler，interval / daily / cron | `app/services/scheduler_service.py` |
| 数据准备 | 数据工厂，可按接口步骤批量造数 | `app/services/data_factory_runner.py` |
| 协议覆盖 | HTTP 与 WebSocket 用例 | `app/services/case_runner.py` |

其中“失败可定位”（执行明细含完整请求响应与断言结果）是 CI 场景最关键的既有优势。

## 4. 缺口清单

| 编号 | 缺口 | 说明 |
|---|---|---|
| G-1 | 鉴权 | 平台当前没有登录与权限模块，任何可访问者都能触发或删除数据，流水线调用必须带凭据 |
| G-2 | 面向流水线的接口契约 | 现有 `/api/*` 面向页面，返回结构服务于 UI；流水线需要明确入参（服务、集合、环境、提交信息）与明确返回（执行标识、结论、通过率、报告链接） |
| G-3 | 触发来源标识 | `TriggerType` 目前只有 `manual`、`scheduled`，需要新增 `ci`。`ExecutionHistory.trigger_type` 为 `String(32)`，新增枚举值不需要数据库迁移 |
| G-4 | 统计口径 | 仪表盘当前只统计 `TriggerType.SCHEDULED` 的执行（`app/services/dashboard_service.py`），CI 触发的执行默认不进统计，需要明确是否纳入 |
| G-5 | 异步执行 | 集合执行同步运行在请求线程中（`app/blueprints/suites.py`），流水线需要等待结果，长集合会超时，多个服务同时触发会排队 |
| G-6 | 并发与部署形态 | 调试状态保存在进程内存、调度器运行在 Web 进程内，导致平台必须保持单个 Gunicorn worker；CI 触发会带来并发峰值，这条约束会首先暴露 |
| G-7 | 幂等与去重 | 同一提交重复触发、连续多次提交时的排队与去重策略 |
| G-8 | 数据与环境隔离 | 流水线执行后测试环境的数据需要可重置，或完全依赖数据工厂现场构造 |
| G-9 | 历史保留策略 | CI 每日多次触发会产生大量执行记录与报告，需要保留周期与清理机制 |

## 5. 触发方式选择

平台无法主动得知业务服务完成了提交，落地时只能是以下三种之一：

| 方式 | 实现成本 | 时效 | 耦合度 | 说明 |
|---|---|---|---|---|
| 流水线调用平台接口（推） | 低 | 即时 | 中 | 被测服务的流水线在部署后调用平台。最可控，建议作为首选 |
| 代码托管平台或部署系统回调平台（推） | 中 | 即时 | 低 | 平台提供 webhook 接收端，需要签名校验与幂等处理 |
| 平台定时轮询仓库或部署系统（拉） | 低 | 有延迟 | 高 | 可复用现有 APScheduler，适合做原型，但不建议作为最终方案 |

## 6. 分阶段路线

### 阶段一：最小闭环

目标：让一条真实流水线能够触发平台执行，并拿到明确结论。

范围：新增面向流水线的触发能力（含凭据校验）、新增 `ci` 触发来源、执行结果可被调用方获知。

验收：

- [ ] 业务服务流水线的某一阶段能够触发指定用例集合执行
- [ ] 调用方能得到明确结论（通过 / 失败）与报告链接
- [ ] 人工在页面触发的执行不受影响

### 阶段二：异步化与并发

目标：解决长集合超时、多服务同时触发的排队问题，并为多副本部署解除约束。

范围：执行与请求解耦（立即返回执行标识，通过查询接口或回调获取结论）、执行器与 Web 进程分离。

验收：

- [ ] 长集合执行不再导致调用方超时
- [ ] 多个服务并发触发时行为符合预期
- [ ] 平台可增加 Gunicorn worker 而不破坏调试与定时任务

### 阶段三：质量门禁与结果治理

目标：从“能触发”走到“能拦住问题”。

范围：失败判定规则、是否阻断发布、结果通知回传、统计口径调整、幂等与去重、历史保留策略。

验收：

- [ ] 可按规则决定流水线是否放行
- [ ] 执行结论能推送到团队常用渠道
- [ ] 历史数据增长可控

### 阶段四：自动感知（可选）

目标：不再依赖业务方流水线主动调用。

范围：提供 webhook 接收端，或订阅部署系统事件。

验收：

- [ ] 业务服务部署完成后平台自动触发对应集合
- [ ] 重复事件不会重复执行

## 7. 实现前需要确定的问题

以下问题属于产品与流程决策，需要在进入开发前明确：

1. **触发粒度**：按“服务”触发，还是按“集合”触发？是否需要维护“服务 → 集合”的显式映射关系？
2. **环境策略**：CI 执行使用独立测试环境，还是与人工验证共用同一环境？执行前后是否需要重置数据？
3. **失败判定**：什么情况算失败？任意用例失败，还是允许一定的错误率阈值？
4. **门禁强度**：失败时硬阻断发布，还是仅告警并记录？
5. **结果回传方式**：同步等待返回、轮询查询、还是回调通知？
6. **并发策略**：同一服务重复触发是排队还是取消先前的执行？跨服务的并发上限是多少？
7. **凭据方案**：使用统一令牌，还是每个服务独立凭据？平台后续建设账号体系时如何演进？
8. **历史保留**：CI 执行记录的保留周期与清理方式。
9. **统计口径**：CI 触发的执行是否纳入仪表盘统计，还是单独呈现？
10. **覆盖范围**：仅覆盖 HTTP 用例，还是包含 WebSocket 用例？

## 8. 不在本方案范围

- 平台自身的 CI（见[技术债与升级计划](./技术债与升级计划.md) TD-3）
- 平台账号与权限体系的整体建设（README 已列为后续规划）
- 多副本部署与任务队列的完整架构改造（阶段二仅涉及必要部分）
- 被测业务服务侧的流水线改造，由各业务团队自行负责
